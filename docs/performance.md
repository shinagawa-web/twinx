# Performance measurements

`perf/` measures twinx releases and pull requests against nginx under the same load, to show the scenarios where twinx spends more than nginx. Recorded only: it is not part of the judge, the twinx loop does not act on it, and a human reads it and opens issues. It was a repository of its own, shinagawa-web/twinx-perf, until it moved here at its commit 2b16a57.

```
perf/run.sh v0.4.0              # measure a tag against nginx, and keep nginx's measurements
perf/run.sh v0.4.0 --quick      # one short round, to try it out (not to record)
perf/run.sh v0.4.0 --group tls  # only one group of scenarios (not recorded)
perf/run.sh --pr 123 --scenario "static 4k" --scenario "TLS, full handshakes"
                                # only the scenarios of these exact names (not recorded)
perf/run.sh --pr 123            # measure the head of a twinx pull request against nginx (not recorded)
perf/run.sh --ref main          # a twinx commit or branch against nginx (not recorded)
```

Only a tag's run of all the scenarios measures nginx: its measurements are kept in `perf/results/<arch>/nginx.json` (`perf/lib/keep.py`) with the tag and the date they were taken, and every other run measures twinx alone and is compared with them. nginx is the same nginx 1.30.6 each time, and it took about a third of the measuring time. A scenario that file does not have, a new one, or one changed since (`definition`, a digest of it), is measured with nginx in the run itself. `perf/results/aarch64/nginx.json` was first taken from `perf/results/aarch64/v0.4.0.json`, which has 7 of the scenarios and no definitions or answers of them.

`perf/run.sh` fetches a tag's binary for the machine's architecture from its release with `gh`, or, when the release has none, builds it from the tag's source in twinx's pinned Rust image; a pull request's head, or a commit, it builds the same way. On macOS all of it runs in the Lima VM named by `$VM` (default `twinx`), in the directory `$VM_DIR` of its home (default `perf-run`). The measuring image (`perf/lib/Dockerfile`) is pulled from `ghcr.io/shinagawa-web/twinx/perf`, to which `.github/workflows/perf-image.yml` pushes it from main, tagged by a digest of the Dockerfile and what it copies (`perf/image-tag.sh`); when it cannot be pulled, it is built.

## Measurements

`perf/lib/bench.py` measures nginx and twinx with the same configuration in one container (`perf/lib/Dockerfile`: the same nginx 1.30.6, with wrk, h2load and openssl) with no network but loopback, in 95 scenarios (`perf/lib/scenarios.py`), each there for a feature of twinx, level with nginx or not: a scenario is there so that twinx spending more than nginx in its feature shows. In a tag's run of all the scenarios both are measured in the same run, so what they differ in does not come from the machine; in the other runs nginx's measurements are those kept, from another runner. The servers are pinned to the machine's first CPU, nginx with one worker as twinx has one; the load, the slow clients and the upstreams run on the others.

The servers are started for each scenario, with only the configuration it needs, so nothing carries over from another, and again for each round: started once, two processes of the same binary differed by up to 21% (gzip_static) though the rounds of each agreed. Before any load, each server's answer is checked, after a first request that fills the cache where a scenario is about what is in it (status, length of the body, the HTTP version, the headers the scenario is about): nginx's against what the scenario expects, twinx's against nginx's, kept with nginx's measurements when nginx is not measured. A server that does not start with the configuration, as a tag that does not know a directive, or does not answer as it should is not measured: it shows "–", and the reason is listed. Each scenario is measured on both servers in turn, five rounds of 3 seconds (nine where the noise was above 5%) in a different order each round, and the median is kept.

| Group | Feature | Scenarios |
|---|---|---|
| http | Connections | `return` with 64 connections, with 1000, with a new connection per request, beside 1000 slow clients |
| | Finding the configuration | a regex location with rewrite and variables, 200 locations, 200 server names |

| config | Finding the configuration | 50 regex locations, 50 wildcard and 50 regex server names, `error_page` to an internal redirect |
| | Headers, logging, files | 18 request headers and a 1 KB cookie, `add_header` of the server and the location merged by `add_header_inherit`, `access_log` to a path with a variable and with a `log_format` of 12 variables, index with alias, `if` and expires, a 1 MB file with sendfile |
| files | Static files | 1 MB, 4 KB, `try_files`, a range, 304 |

| | First byte | `return`, TLS, HTTP/2, proxied as it comes |

Each group is a job of its own in CI, on a runner of its own, so servers are only ever compared within one. `s_time` counts the connections that were not resumed when they were to be, or were when they were not, as errors; the proxying table shows how many connections to the upstreams a request took.

Not measured: OCSP, stapling, HTTP/2 connections during a reload (h2load does not connect again after the GOAWAY), and directives that only set a limit, a timeout, a path or a size, `proxy_limit_rate` among them (`limit_rate` too: twinx does not slow an answer it can send within a second, so it is not like for like with nginx), and revalidation (`proxy_cache_revalidate`): nginx keeps an answer for a second at least, so under load all but a few requests a second are the HITs measured already.

The summary (`perf/lib/compare.py`) starts with the scenarios where twinx took more CPU time per request than nginx, with twinx's over nginx's, the most first: where the load generator is the limit, rps does not show it. CPU time per request differs somewhat between runners, so only the scenarios far above nginx are worth working on. Memory comes next, for the scenarios there for it, with twinx's peak over nginx's. It then has, folded away, a table each for throughput and latency, CPU and memory, the sockets' queues (accept queue, Recv-Q, Send-Q, listen queue overflows, retransmissions), proxying, and slow clients; each cell is nginx / twinx, and the summary says in how many scenarios nginx's were kept and from which tag. The configuration uses only what twinx accepts: it does not know `worker_connections`, so that is given to nginx alone, and so is `worker_processes`, which twinx takes but always serves from one worker.

Measurements run in the `perf` workflow (`.github/workflows/perf.yml`; Actions, Run workflow, with a tag, a twinx pull request number or a commit or branch, and the scenarios) on aarch64 runners: the questions do not depend on the architecture, and x86_64 runners change CPU model from run to run. `scenarios` takes the names of scenarios as the summary and `perf/lib/scenarios.py` have them, separated by commas, such as `static 4k, TLS, full handshakes` (a name has commas of its own, so the list is read as the longest names it starts with); a name that is not a scenario stops the run before anything is measured. The scenarios named are measured in one job, whatever their groups. A pull request or a commit has to name its scenarios; `all`, the default for a tag and taken only with one, measures every scenario, ten jobs side by side, in about 15 minutes. A tag's results of all the scenarios are committed to `perf/results/aarch64/<tag>.json` on the branch the run is started on, which cannot be main (main takes changes only through pull requests), and, when the branch has an open pull request, put in one comment there (`perf/lib/comment.sh`) that each later run replaces. A pull request that changes `perf/`, `perf.yml` or `perf-image.yml` runs the workflow too, on one scenario (`return, 64 connections`) of twinx's latest release in one short round (`--quick`), to check in a few minutes that measuring still works, and gets the results in one comment that each later push replaces; nothing is committed. Other pull requests do not run it. For a twinx pull request, `perf/run.sh` builds its head, and it is measured alone against nginx's kept measurements; the results are shown in the run's summary, put in one comment on the pull request that each later run replaces, and kept as an artifact; nothing is committed.
